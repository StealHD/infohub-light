## 11. 后台任务合同
异步、批量、定时、长耗时任务必须定义任务状态合同。

至少说明：

1. 任务 ID
2. 状态枚举
3. 进度字段
4. 成功 / 失败 / 部分成功结果结构
5. 超时策略
6. 重试策略
7. 并发或速率限制
8. 结果保留周期

当前任务边界：

1. 两份 compose 的运行单元固定为 `horizon-api + horizon-worker`，不存在 scheduler profile 或旧发布器进程。
2. 单源刷新、用户 Feed 刷新与周期计划都由 Worker 异步任务执行。
3. Full-text、article graph、静态站发布与日报摘要链已退役；API、Worker 和 React 不得重新引入这些 writer 或读取其历史文件。
4. API 与 Worker 的 runtime/operation 日志写入 `logs/**`，UTC 每日轮转且默认保留 30 天；原始文件不进入 Agent 上下文，只有 5B 定义的当前用户脱敏结构化事件可由 OpenClaw 查询。
5. 响应结构诊断只在 adapter 收到上游值时即时提取字段路径/类型，原始值随调用栈释放；Job 只保留有界双层摘要，Feed snapshot、稳定内容索引和媒体记录不得保存该诊断。

### 11.1 信息流触底文案生成

1. `workspace_feed_end_messages` 是幂等新增的 workspace 级 SQLite 缓存表，保存三个列表、非敏感配置指纹、generation、刷新状态、原子租约、最近尝试/成功/下次刷新/退避时间和安全错误码；不保存提示词、模型原文、用户内容或密钥。指纹必须包含当前文案安全合同版本，因此 prompt、白名单或校验语义升级会把旧缓存标成待刷新而不需要数据库迁移。
2. 始终存在内置中文列表。显式触底 Key/模型或独立生成开关未就绪时，GET 必须忽略旧 AI 缓存并返回 `source=builtin,status=disabled`；重新开启后，配置变化、手动刷新、到期或首次缺少缓存均可进入 pending，后台生成期间仍可返回上次通过校验的 AI 列表。旧空绑定仅保留读取兼容，仍临时受工作区 AI 开关控制。
3. Worker 只有在普通任务队列无法 claim Job 时才检查触底文案；一次 idle 轮询最多 claim 一个 workspace、记录一个 workspace AI attempt，并发起至多一次 60 秒模型请求。该调用关闭 SDK 自动重试，不创建普通 Job，也不由 scheduler 驱动。
4. 模型结果必须是只含 `empty/first_end/repeat_end` 的 JSON object；每个数组恰好等于配置条数，三个数组全局去重。每句必须为 trim 后 4–40 字的单行简体中文纯文本，禁止 HTML、Markdown、URL、催促、羞辱、焦虑表达和虚假完成声明。每句可选且最多带一个克制装饰，白名单为 `🙂/😊/🌿/☕/✨/📚/🍵/🌙/🫧/^_^/:)/:-)/(・ω・)/(´▽｀)/(｡･ω･｡)`；`☕` 的标准 emoji variation selector 视为同一装饰，其他 Emoji、颜文字或多个装饰均拒绝。自定义风格不得覆盖这些约束。
5. 成功后 generation 原子加一并按 `refresh_days` 安排下次刷新。超时、配额、调用或输出校验失败只写安全错误码，保留上次成功列表；从未成功则回退内置列表。失败固定六小时后才可自动再试，手动刷新或配置指纹变化可提前触发。

## 12. Feed v2 显式迁移合同

实现中存在迁移脚本不代表任意部署数据库已迁移；当前本地目标部署已于 2026-07-11 显式迁移并验收，是否完成仍必须逐个目标数据库以 migration marker 与 readiness 为准。其他旧库不得沿用本地部署结论，仍需逐库显式执行并验收。

1. 未记录 v2 migration 且存在旧 snapshot/item/state，或存在 queued/running 的 `source_fetch/user_feed_refresh` 时，readiness 返回 `migration_required`，Worker 拒绝执行 Feed 任务；只有真正无这些现役 Feed 遗留产物的新库才可自动记录空库 v2 marker。旧 feedback 表与行不参与判定。
2. 应先停止 API 与 Worker，再运行 `python scripts/migrate_user_feed_v2.py --data-dir data --backup-dir data/backups --apply`；不带 `--apply` 使用 SQLite 只读连接检查，不建表、不增列、不写 migration marker。
3. apply 必须先生成 UTC 时间戳 SQLite 备份，再取消未完成 Feed job、清空旧 snapshot/item/state、创建 v2 唯一索引、写 migration 记录并通过 `PRAGMA foreign_key_check`。既有 feedback 表与行不得读取、清空或改写。
4. 应用启动不得自动清空旧 Feed 数据；真实环境迁移属于显式运维动作。
5. 已完成迁移时重复 `--apply` 必须返回 `already_migrated` 且不备份、不清空 v2 数据；备份权限固定为 `0600`，`data/backups/` 不进入 Git。

## 13. User content v5 与 DeepSeek 分析合同

`user_content_items` additive 增加 `analysis_input_hash` 与 `unresolved_reason`。`analysis_input_hash` 是模型无关的来源输入 SHA-256；正文或来源元数据真正变化时才变化，不得因模型切换或历史修复而伪造新分析。

历史修复 CLI 固定为：

```bash
python scripts/repair_user_content_v5.py inspect --data-dir data --output /tmp/content-repair.json
python scripts/repair_user_content_v5.py apply --data-dir data --backup-dir data/backups --cache-legacy-media
python scripts/repair_user_content_v5.py reconcile --data-dir data --backup-dir data/backups
python scripts/repair_user_content_v5.py enqueue --data-dir data --free-only
```

1. 报告固定包含 `status/counts/repaired_body/repaired_media/enqueued_sources/unresolved/backup_path`。
2. inspect 使用只读 SQLite；apply 必须拒绝活跃 Worker、先生成 `0600` 备份，再校验 integrity/foreign keys 并写 version 5 marker。
3. reconcile 必须在任何 `queued/running` Job 或活跃 Worker 存在时于备份前拒绝；有变更时先生成 `0600` 备份，再事务性把 `unresolved_reason` 升级为 nullable，并只从非空 `captured` 正文移除精确 token `source_body_not_available`。其他 reason 必须保留；无剩余 reason 时写 SQL `NULL`。重复运行返回 `already_reconciled` 且不创建备份。
4. `content_repair` 只更新已有 `user_content_items` 的正文、媒体、哈希和 unresolved reason；新抓到的 article 必须忽略，结果固定声明 `snapshot_created=false`、`analysis_calls=0`。
5. 免费来源允许批量入队；Apify social 等付费来源不得由 `--free-only` 入队，必须报告 `paid_source_requires_authorization`。不建设网页全文代理。
6. 详情 `captured` 返回来源接口已有正文；`excerpt_only` 明确降级。媒体最多 6 张且只返回鉴权 `/api/media/*`，不得返回上游临时 URL。

AI Secret metadata 的 `kind=ai` provider 允许 `deepseek`；真实值仍为 write-only。DeepSeek 默认模型和环境变量名固定为 `deepseek-v4-flash`、`DEEPSEEK_API_KEY`，Base URL 缺省时由客户端使用官方地址。

分析复用顺序固定为：当前模型精确 cache → 同用户、同 article、同 input hash 的其他模型安全 cache → 同 input hash 的稳定安全 AI 投影 → 当前 provider。跨用户、输入变化、fallback/excerpt 原文均不得复用。跨模型复用必须记录原模型或 `stored-content`，不得把旧结果标记为 DeepSeek 产物。真实启用前，`scripts/deepseek_analysis_smoke.py` 必须先以 10 秒超时、SDK retry=0 调用 `models.list()` 并确认精确模型；预检失败时 completion 为 0，成功后才允许对一篇 captured article 做恰好一次 completion。该 completion 必须省略 `temperature` 并禁用通用客户端的应用层参数降级重试，首次失败即终止。stdout 只含 provider、model、token 用量和 status。

22. 四种 goal 都通过持久 Pool Stage 执行。plan hash 必须覆盖 goal、人工候选集合与服务端冻结顺序、服务端解析的 Actor/Build/Manifest、Route generation、基础 pool hash、当时所有 enabled source 的 binding generation/target fingerprint、逐项费用与批次上限。一次 `confirmation="确认付费验证主备"` 审批原子创建 batch、stage、候选 validation、来源快照和唯一 one-shot Job；Worker 严格按服务端冻结顺序先完成 Route Canary，再在同一批准上限内预验证快照中每个 enabled source 的目标槽。`initial_pool` 成功目标按 Route 最低值为 X/Instagram 标准 2/3 或 YouTube fallback 1/3；`upgrade_legacy` 在原 legacy 池持续服务时旁路验证三个 exact-Build Actor并最终整体替换为 3/3，旧 lifecycle 不得改写；`complete_third` 只验证管理员明确选择的新增备份且原槽全程不变；`compatibility_single` 只验证并旁路准备一个兼容 Actor。已通过付费验证的 probationary Revision 立即具备运行资格，后台认证观察不阻塞 staged apply。新增、binding 变化或失败来源使 stage 保持未就绪，下一 plan 只覆盖当前缺失证据并复用已有成功；禁用或删除来源不再阻塞。unknown-start 与费用待对账阻断后续付费和 apply，任何重试或增量计划都需要新的有界人工审批。
23. Staged apply 复用 `POST /api/admin/apify-routes/{route_id}/active-pool/activate`，并携带 `stage_id`、`expected_plan_hash`、`apply_id`、最新 Route generation 与既有确认词。服务在一个 `BEGIN IMMEDIATE` 中重新校验基础池、执行模式对应的 Build/Manifest 要求、Actor/发布者门槛、batch 所有 item 与费用均已终结、无 inflight/unknown-start、以及当前所有 enabled source 对目标池都有匹配当前 fingerprint 的成功证据；任一条件变化必须零写入 fail closed。成功时原子写入目标槽、Route generation、对应 `ready_1of1|ready_2of2|ready_3of3` 来源状态与 stage 终态；精确 `apply_id` 重放返回同一结果，跨 stage/plan 复用冲突。Route detail 只投影服务端计算的 `workflow/next_action/progress/blockers` 和每个 Revision 的后台认证进度；当 staged approval 需要重新计划时，`workflow.progress.last_failure` 最多包含阶段、规范化安全错误代码、最终或待对账费用及终态标记，不得投影 candidate ID、来源 target/fingerprint、approval hash、远端 Run/Dataset ID、上游错误或内部输入。基础 Stage 能力由离线 migration `apify_actor_pool_staging_v18`（global version 20）安装；人工候选与目标槽数由后续 `apify_actor_manual_pool_selection_v19`（global version 21）增加 `target_slot_count/selection_mode` 并把既有 Stage 安全回填为 `server` 模式。global 21 要求 global 20 已通过、API/Worker 停止且无活跃 ActorOps Job，使用 SQLite backup API 创建 `0600` backup并检查完整 marker/table shape、integrity 与 foreign keys；任何失败恢复备份，普通 initialize、API 与 Worker 不得静默升级，readiness 在显式迁移前返回 503。
24. Validation tuning 由离线 migration `apify_actor_validation_tuning_v20`（global version 22）安装。普通 Stage Candidate 冻结 `timeout_seconds=180..900`、`sample_items in (1,3,5)`、`max_charge_usd<=0.10` 与 profile hash；非 1 的样本数只在 Manifest 确实引用 `runtime.max_items` 时可用。`upgrade_legacy` 收紧为固定 300 秒、样本 `1|3` 和不超过当前 Route `$0.02` 上限：只有已终结 `suspicious_empty` 且 Manifest 支持数量时可从 1 调到 3，样本 3 仍失败即停止；不得改为 5、提价、延时或更换 Actor。plan hash、CAS、approval 幂等和 Worker Run 都使用同一冻结配置，不得回退到容器全局超时。Validation 持久化耗时、Dataset/有效行数和由 Route、opaque Candidate、exact Revision/Build/Manifest、加盐目标指纹、validation kind 与 profile 组成的失败指纹；同指纹新计划以 `409 apify_actor_validation_profile_unchanged` 在 Actor POST 前拒绝并记为 `$0`。状态读取失败只允许 reconciliation，不得生成新付费计划。`POST /api/admin/apify-routes/{route_id}/validations/reconcile` 只按已知 durable reservation 重读原 Run/Dataset，不调用 Actor POST，也不 abort 仍在运行的 Run；批次恢复状态与续跑 Job 在同一事务内继续原审批已覆盖的剩余来源检查，不得扩大候选、费用或自动重试。global 22 需要 global 21，停 API/Worker、跨过 heartbeat 安全窗且无活跃 ActorOps Job，建立 `0600` backup、回填旧 Validation 为 300 秒/1 条/原审批上限，并通过 integrity/foreign-key/table-shape 后才提交 marker；失败必须恢复备份。
25. `GET /api/admin/sources/{source_id}/apify-support` schema 2 投影唯一 `next_action`。若下一 active Revision 是 `legacy_builtin` 或缺少 exact Build/Manifest，返回 `upgrade_pool_required` 和安全原因 `apify_actor_source_requires_pool_upgrade`，对应槽位为 `blocked` 且 `can_canary=false`；`POST .../apify-validations/{revision_id}/canary` 在预算、Validation 和 Job 写入前以 412 再次拒绝。该阻断费用为 `$0`，历史失败只用于诊断，不得让浏览器继续生成注定由 Worker 拒绝的付费任务。只有全部 populated slots 在当前 target fingerprint 下成功且 binding 尚未 ready 时才投影首次启用确认。
26. 第 24 条取代第 6 条中“超时只由容器环境变量热加载”与第 8 条中“每次固定 `maxItems=1`”的限制；容器变量只保留为旧流程默认值，Stage Validation 以数据库冻结 profile 为唯一权威。人工 Stage 的 Route 部分最多三个 Candidate 且每个最高 `$0.10`，因此 batch/route-validation 表约束上限为 `$0.30`；包含 enabled source 预验证的整个 Stage 仍受 `$6.06` 硬上限保护。
27. ActorOps resilience v21 由离线 migration `apify_actor_resilience_v21`（global version 23）安装，并取代本节第 1、3、5–8、10、14、16、21–25 条中“少于两路永远不可运行”“缺少 Store Schema/Tagged Build/可证明 Manifest 永远不可验证”“非 exact Build 永远不可执行”以及“空结果或旧 Dataset 可直接增加成功计数”的限制。标准模式仍建议至少两个 Actor、两个发布者，Route 仍保留三槽；严格 Discovery shortfall 后，Owner/Admin 可明确选择 `goal=compatibility_single`、`target_slot_count=1`。兼容候选跨免费检查 Run 保留同 Route 的最新安全 Revision，后续空搜索不得把已经符合兼容硬底线的单个候选归零；Build、Schema、价格或失败指纹变化时仍以该 Candidate 的最新 Revision 重新判定。兼容候选必须公开、明确可运行、不要求完整权限且单次价格不超过 Route `$0.02`，输入只允许受控 handle、URL、标准 `startUrls` 与数量字段；deprecated、缺少 Store Schema/Tagged Build 或预先可证明 Manifest 只产生风险警告。一次独立付费确认后，兼容 Canary 必须在固定公开参考目标上返回通过身份、内容 URL、发布时间、正文及占位/付费墙检查的真实非空内容；空结果不能证明单路可用。输出可生成观察型 Manifest；实际 Build 可取得时固定 Build，否则以 `execution_mode=current` 跟随当前 Build，并在每次运行继续执行完整输出合同和 publication fence。Canary 内容成功但费用尚未终结时，Stage 保持待对账；费用 reconciliation 只能复用原 Run 的终态证据，在 `cost_final` 后原地晋升 Revision 与 Stage，禁止再次 POST Actor。第二次无费用确认原子启用 1/3 兼容池，Route 的 `admission_mode=compatibility`、实际最低槽位和发布者数均为 1，X `source-types.availability` 变为 `ready`；旧池和既有来源在确认前不迁移、不停用。后续可不停机补位或升级回标准模式。
28. 运行结果必须在日期过滤、目标身份和 publication fence 后再判定语义。每个 Apify 来源持久化不含正文的水位线：最新发布时间、稳定内容 ID 的哈希集合摘要与最近推进时间。出现新内容为 `advanced`，推进水位并计成功；只有已见内容为 `no_advance`，不增加成功计数；最新结果早于水位为 `stale_regression`，立即尝试下一可用槽并记录旧数据故障；`valid_empty/suspicious_empty` 继续结合目标历史和主备证据判定。`apify_source_route_bindings` 保存来源级软首选 Candidate；`PATCH /api/admin/sources/{source_id}/apify-preference` 只接受 `candidate_id|null` 与 binding generation，改变优先顺序而不硬锁 Actor。首选失败、旧数据或暂停时自动切备；连续两次新鲜度通过后才恢复首选，且来源之间互不影响。普通来源 API、配置和新增表单仍不得返回 Actor、Build、Route、Key 或内部 binding。
29. Key Pool 公开响应升级为 schema 2，每个成员投影 `role=acquisition|validation`，整个工作区最多一个独占校验 Key。`PUT /api/admin/apify-key-pool/validation-key` 以 pool generation 指定或取消；指定前不得有该 Key 的非终态 Run，生产 Key 必须先完成既有安全排空。validation Key 不参与生产排序、轮换或生产 Key 耗尽兜底；Run 持久化 `purpose=acquisition|validation`，校验 Key 故障只阻断校验。兼容 Canary、ActorOps Canary 和新鲜度检查优先使用校验 Key；没有指定时人工 Canary 保留旧兼容路径，自动新鲜度必须阻断且不能借用 acquisition Key。
30. 每条 Route 的自动新鲜度设置缺省关闭、建议间隔 24 小时，允许 6–168 小时或关闭。启用或改变频率必须携带新的站立授权确认和 Route generation；`GET .../freshness-plan` 返回当前 Actor 数、串行执行、单 Actor/单轮上限、上次实际费用、下次时间和按频率计算的理论月上限，真实公开参考账号只保存为内部轮换编号，不返回目标。`POST .../freshness-checks` 是一次单独费用确认的手动检查，必须回传用户看到的精确 Route generation 与单轮总费用上限；任一值在弹窗期间变化就以冲突拒绝且不创建 Job。检查排队或运行期间不得替换、重排活动池，任务开始时还要再次核对冻结的 Route generation；远端费用延迟结算时只幂等对账既有 Run，不重发 Actor POST。自动和手动均创建 `apify_actor_freshness_check` one-shot Job，使用同一目标、同一窗口和有界样本串行比较，不自动 Actor POST 重试。三路用多数最新指纹确认落后者；两路差异先记 `suspected_stale`，连续两次或来源水位倒退后确认；单路只验证可运行与结果时效并标记无法交叉验证。恢复需要连续两次新鲜度通过。任一轮部分失败等待下一周期，任务去重保证同 Route 只有一个非终态检查。
31. Actor 评估历史以 Route、Actor、Build/Schema/价格指纹、策略模式和阶段为键，保存稳定原因码、次数与首末时间。相同指纹的确定性失败在 AI、input validation 或新的付费计划前跳过；Build、Schema 或价格指纹变化后可重新评估。管理员可请求一次 `POST /api/admin/apify-actor-evaluations/{evaluation_id}/retry`，历史不删除，涉及费用仍需新的明确确认。YouTube 继续以 Atom Feed 为主链路，fallback 一路即可运行；既有两路保留，系统不自动追逐第三槽，新增备份只由管理员主动发起。
32. `GET /api/admin/apify-actor-events` 是 Owner/Admin 数据库型诊断时间线，可按 Route、来源、opaque Candidate、阶段、结果和时间过滤；默认 24 小时、最多 30 天、游标分页且每页最多 100 条。事件跨 Discovery、静态检查、Canary、费用对账、运行切备、新鲜度、Key 与人工操作，只返回公共 Actor 名称、稳定原因码、有界计数、最终费用和 request/job 关联；Token、真实目标、输入、正文、远端 Run/Dataset 和原始错误永不进入表或响应。事件在业务事务提交后写入并镜像为结构化 operation event；镜像失败不回滚业务。30 天保留由有界维护删除。
33. v23 新增/更新的 Owner/Admin 接口为 `PUT /api/admin/apify-key-pool/validation-key`、`PATCH /api/admin/apify-routes/{route_id}/freshness-settings`、`GET /api/admin/apify-routes/{route_id}/freshness-plan`、`POST /api/admin/apify-routes/{route_id}/freshness-checks`、`GET /api/admin/apify-freshness-checks/{check_id}`、`PATCH /api/admin/sources/{source_id}/apify-preference`、`GET /api/admin/apify-actor-events` 和 `POST /api/admin/apify-actor-evaluations/{evaluation_id}/retry`。Route detail 增加 `admission_mode`、实际最低槽位/发布者、兼容风险、freshness 与各槽新鲜度；Pool Candidate/Stage 接受 `compatibility_single` 并投影安全评估历史。所有 mutation 继续使用其对象 generation 或独立费用确认，不得混用；公开新增来源接口保持脱敏。
34. global 23 精确依赖 global 22；现有 Route 默认 `standard`，不自动启用兼容模式、不指定校验 Key、不启用自动新鲜度，YouTube fallback 的实际运行最低槽位改为 1。迁移必须停止 API/Worker、跨过 heartbeat 安全窗、确认无非终态 ActorOps Job，使用 SQLite backup API 创建 `0600` 备份，再执行 marker/checksum、完整表形状、`PRAGMA integrity_check` 与 `foreign_key_check`；任何失败恢复备份。普通 initialize、API 和 Worker 不得静默升级，readiness 在显式迁移前返回 503。迁移不联网、不调用 AI/Actor，也不创建费用。
