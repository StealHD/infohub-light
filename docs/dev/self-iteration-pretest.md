本说明供受信操作者组织本次隔离联调使用，不构成新的规则真源。测试选择、审查顺序和门禁仍以[测试与控制面验证](test-gate.md)为准，开发端职责、证据边界及工作记录归属仍以[项目指引](../../AGENTS.md)为准。本次只讨论三条独立的测试任务：同意、暂缓、拒绝；它们不是同一个任务的重复审批，也不以某一模式的结果替代另一模式的验收。

本轮从固定候选 `c829343f96c320381f6c3029cff3ab251748bf41` 开始，使用独立分支 `iterate/pretest-20261003-fix`。候选、分支和后续检出身份必须由控制端核对；身份不一致、完整 SHA 无法核实，或审计结果未知、审批已过期时，立即停止，不以短 SHA、近似提交或工作区状态代替候选。每一任务在同一关只需一张有效卡。版本变化后必须创建新上下文，并使旧卡失效；不得沿用旧卡批准新候选。

同意模式仅对该审批卡明确列出的操作和候选有效，不能外推至其他任务、分支、版本或环境。现有 `receipt_only` 接口只保存回执，不会自动授予开发、构建或部署权限。本次开发由当前人类会话另行授权，不能从回执、历史授权或其他任务推断。暂缓和拒绝均不得进入领取执行，且不影响其他任务继续按各自状态处理；暂缓不会自动恢复，拒绝也不会自动重试。恢复暂缓或重新处理拒绝，均须在新的、可审计上下文中由本人明确处置。

通知标题建议以实际修复任务名称为主体，例如“修复订阅列表加载失败”，任务编号仅用于追溯。任务名不能使用 `step` 编号作为最终名称。每张可核对的任务卡应写明任务名、问题摘要、具体动作、影响目标、分支及候选完整 SHA、已完成验证、未完成项和停止条件，使审查者能将文字、候选和审计记录逐项比对。这只是后续改善名称展示的建议；本次不修改真实通知程序，也不声称通知行为已经改变。

暂缓必须保留暂缓原因和可重看条件，拒绝必须保留拒绝原因。本次真实拒绝事件的原因为空，因此“原因留存”验收尚未通过；应由本人补充备注，并保留原事件，不得伪造、覆盖或重写历史来补齐证据。记录只保留任务所需的审计事实，不写入个人账号、聊天 ID、IP、密钥或私有路径。

隔离开发端在本轮只生成此文档。当前 Codex 控制端应独立审查其事实、范围与链接，并依项目门禁在本地完成候选验证；文档不能替代该审查或门禁。本轮并非经原 Multica Agent 自动派发。开发端交付文档时，尚未取得控制端的审查、门禁或新提交证据；这些结果须在实际完成后另行记录，不得由开发端预先声称成功。本关不包含推送、新 PR、构建、合并、部署或审批程序修改，不能宣称全部模式验收完成。下一关只能绑定完成审查和门禁后的固定候选，再向本人请求相应授权；未满足任一前提即停止，等待新的明确指令。
