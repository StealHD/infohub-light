### D126 OpenClaw 附件摘要采用满宽行、按需上浮与快速清空

- 决策日期：2026-08-07
- 当前状态：原 UI 任务分支修正与验证中；不改变上下文记录、Gateway handoff、API 或数据库。
- 决策内容：Composer 内可点击的附件行统一占满可用宽度，来源链接消费剩余空间，移除按钮固定对齐同一右边线；长标题只在链接轨道内截断。超过两条时，摘要头把“已附带 N 条”与紧随其后的向上 Chevron 合为至少 32 px（粗指针 44 px）的整段点击区，并占据清空图标之外的全部可用宽度；它让原摘要容器使用 deliberate-motion 向上拉伸，仅显示尚未显示的满宽行。最右的中性清空图标立即持久化空附件数组，不确认、不发送、不改变问题文本；清空或缩减为两条时收起剩余区。一至两条只显示静态数量与清空，不渲染重复展开入口或第二个窗口。
- 原因：内容宽度的 inline source 会让短标题的移除按钮提前结束，形成参差的右边线；在已经完整显示一至两条时继续提供入口没有信息增益，而重绘前两条会制造重复。满宽轨道和原位、仅含剩余项的上拉伸使列表边界、操作位置、展开方向和信息增量都可直接预期；大点击区与快速草稿清理则让高频操作更容易命中而不波及问题文本。

### D132 OpenClaw 图片对话使用浏览器规范化与 Gateway 媒体票据

- 决策日期：2026-08-07
- 当前状态：Inteliscope 实现与完整门禁验证中；图片开关默认关闭，Gateway 票据 RPC 仅作为安全输出/历史图片的可选扩展。
- 决策内容：OpenClaw 对话只接受 JPEG、PNG、WebP 图片，浏览器在当前页面内完成尺寸、像素和字节上限检查，最长边缩至 2048 px 后重新编码为 WebP，移除 EXIF 和原文件名。每轮最多四张，单张不超过 5 MiB、总计不超过 12 MiB；原始文件/Base64 不写入 Inteliscope 服务、日志、数据库或 sessionStorage。图片输入复用原版 Gateway 已有的 `chat.send.attachments`，只要求功能开关和当前模型声明 `image` 能力。历史和输出不信任任何内容块 URL：页面只读取 `messageId + partIndex`，仅当 Gateway 声明 `chat.media.ticket` 且返回 allowlisted 路径时，才获得 5 分钟、单图绑定的 Gateway 路径与票据，刷新/重连后重新申请；缺少该 RPC 时继续支持文本和图片输入，但不显示 Gateway 输出/历史图片。Handoff 升级 V7，只记录 `imageCount`，并明确图片/OCR 为不可信用户内容。
- 云端边界：浏览器 WebSocket 与媒体可统一为同一 Gateway Origin；Inteliscope 仅配置 WSS 地址和精确 HTTPS 媒体 Origin。Gateway 负责验证 `operator.read`、会话/消息归属、图片类型和允许媒体目录，再代理媒体；对象存储和长期凭据不暴露给浏览器。多副本必须共享历史/媒体索引、持久化媒体和带 `kid` 的票据签名密钥，轮换期同时接受当前及上一把密钥至少一个票据 TTL。CSP 与 `gateway.controlUi.allowedOrigins` 都只接受精确 Origin，禁止通配符。
- 原因：既有 Gateway 的媒体 URL 可能要求浏览器转发长期设备凭据，不能作为跨 Origin Inteliscope 页面图片地址；直接渲染模型返回外链又会造成跟踪、路径和内容类型绕过。把一次性授权收回 Gateway，并让前端只处理内存中规范化输入和短期 ticket，才能同时保持本机、云端和旧 Gateway 的兼容边界。

### D136 ActorOps 以持久 Pool Stage 完成第三槽与零中断 legacy 升级

- 决策日期：2026-08-09
- 当前状态：本地任务分支实现与验证中；不迁移共享数据库、不替换共享容器、不支持手填外部 Actor。
- 决策内容：两路快速池继续先上线，但 Primary/Backup 1 均达到 exact-Build certified 后，管理员可启动 `complete_third` Pool Stage。系统选择与现有池不同的 Actor/发布者，冻结基础池与 enabled 来源 binding 快照，在一次有界付费审批中串行完成 Route 和全部快照来源的缺失验证；第二次无费用确认只原子填入 Backup 2，原两槽全程不变。含 `legacy_builtin` 的池使用 `upgrade_legacy` 在旁路建立两个不同 Actor/发布者的 exact-Build 新池，旧池持续服务，全部来源验证后才原子切换；legacy Revision 只保留为历史，不能原地改成 certified。审批后新增、变化或失败的来源仅生成缺失证据的增量计划，禁用或删除来源不阻塞 apply；unknown-start 继续全链路熔断且不自动重放。
- 状态与审批边界：Route detail 负责计算 `workflow/next_action/progress/blockers` 和自动认证进度，浏览器不按槽数猜动作，也不提交 Actor、Revision、槽位或来源集合。正常 setup、第三槽和 legacy 升级都收敛为免费准备、一次付费确认、一次生效确认；apply 重新校验 generation、基础池、Build/Manifest、终态费用、inflight/unknown-start 与所有当前 enabled 来源证据，并在同一事务写入槽位、来源 ready 状态和 stage 终态。页面使用抓取类型选择器与“主备配置 / 来源启用 / 运行与告警”任务页签，默认隐藏机器状态、Build、费用账本与 AI 细节；probationary 明示自动观察且没有手工转正按钮。
- 取代关系：本决策取代 D110 中“已有安全两路后 UI 隐藏第三槽付费入口”的结论，也取代 D118 的高密度 Route 表与纯视觉迁移边界；D103 禁止浏览器手填/部署外部 Actor、D109 服务端排槽、D110 两路快速上线和 D112 一次审批串行验证的其余安全结论继续有效。
- 原因：第三槽和 legacy 替换此前在 UI 与服务端计划中均不可达，管理员只能看到空槽或兼容标签，却没有安全动作；直接替换 active slots 又会让尚未验证新 Revision 的来源进入空窗。持久 sidecar stage 将付费证据、来源快照和最终切换分离，使现有线路在所有预验证完成前保持权威，同时让刷新、重启、增量补证、幂等与 CAS 都可恢复审计。

### D137 ActorOps 由管理员选择安全候选且验证后立即可运行

- 决策日期：2026-08-10
- 当前状态：任务分支实现与验证中；共享 schema 21 与 8080 切换仍需单独授权。
- 决策内容：服务端为每条 Route/goal 提供经过公开性、能力、费用与安全边界预筛选的 Candidate 列表，管理员决定 allow-list 成员；首次配置和 legacy 升级恰好选择三个不同 Actor且至少覆盖两个发布者，补 Backup 2 恰好选择一个与当前池不同的 Actor。浏览器只提交 opaque Candidate ID，不提供粘贴 Actor ID，也不能选择 Revision、Build、Manifest、槽位或来源；服务端重新解析并冻结 exact Build、决定安全槽位顺序，且绝不静默尝试未选择的 Actor。候选刷新免费，正常流程只有一次有界付费验证和一次无费用生效确认。
- 运行与失败边界：manual `initial_pool`、`complete_third`、`upgrade_legacy` 都使用 Pool Stage，在一次付费审批中串行完成 Route 与当时全部 enabled 来源预验证；initial/legacy 原子生效完整 3/3，第三槽只填 Backup 2。exact-Build Primary/Backup 1 为 probationary 或 certified 都可补第三槽；新 Revision 通过付费验证即显示“已验证，可运行”并允许 apply，48 小时、参考来源和成功率认证继续在后台观察但不再卡配置。stale、内容不兼容、Build 漂移、超时、待对账与 unknown-start 都使用“原因—影响—下一步”且 fail closed；运行记录隐藏成功的 Discovery/批次内部任务，付费失败不提供通用重试。
- 迁移与取代关系：`apify_actor_manual_pool_selection_v19` 使用 global schema 21，为既有 Stage 增加并回填 `target_slot_count/selection_mode`；显式离线迁移仍要求停 API/Worker、无活跃 ActorOps Job、`0600` backup、integrity/foreign-key 与失败恢复。D137 取代 D136 中“服务端独自选候选”“补第三槽必须等待 certified”“legacy 只建立两路”的产品选择；D136 的持久旁路、来源预验证、原池不中断、增量补证、原子 apply、幂等/CAS/费用与 unknown-start 安全边界继续有效。D103 仍禁止创建、部署或手填外部 Actor。
- 原因：管理员的真实任务是明确补全三路，而不是理解 Discovery Job、Revision 生命周期或内部审批状态。把选择权限制在服务端预筛的 Candidate allow-list 内，可让人明确决定池成员，同时继续由服务端掌握 exact Build、槽位、来源证据和付费安全；把稳定性认证从配置门槛降为后台观察，也避免已经验证可运行的 Actor 被 48 小时等待无谓卡住。
