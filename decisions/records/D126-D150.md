### D126 OpenClaw 附件摘要采用满宽行、按需上浮与快速清空

- 决策日期：2026-08-07
- 当前状态：原 UI 任务分支修正与验证中；不改变上下文记录、Gateway handoff、API 或数据库。
- 决策内容：Composer 内可点击的附件行统一占满可用宽度，来源链接消费剩余空间，移除按钮固定对齐同一右边线；长标题只在链接轨道内截断。超过两条时，摘要头把“已附带 N 条”与紧随其后的向上 Chevron 合为至少 32 px（粗指针 44 px）的整段点击区，并占据清空图标之外的全部可用宽度；它让原摘要容器使用 deliberate-motion 向上拉伸，仅显示尚未显示的满宽行。最右的中性清空图标立即持久化空附件数组，不确认、不发送、不改变问题文本；清空或缩减为两条时收起剩余区。一至两条只显示静态数量与清空，不渲染重复展开入口或第二个窗口。
- 原因：内容宽度的 inline source 会让短标题的移除按钮提前结束，形成参差的右边线；在已经完整显示一至两条时继续提供入口没有信息增益，而重绘前两条会制造重复。满宽轨道和原位、仅含剩余项的上拉伸使列表边界、操作位置、展开方向和信息增量都可直接预期；大点击区与快速草稿清理则让高频操作更容易命中而不波及问题文本。

### D132 OpenClaw 图片对话使用浏览器规范化与 Gateway 媒体票据

- 决策日期：2026-08-07
- 当前状态：Inteliscope 实现与完整门禁验证中；图片开关默认关闭，Gateway 票据 RPC 仅作为安全输出/历史图片的可选扩展。
- 决策内容：OpenClaw 对话只接受 JPEG、PNG、WebP 图片，浏览器在当前页面内完成尺寸、像素和字节上限检查，最长边缩至 2048 px 后重新编码为 WebP，移除 EXIF 和原文件名。每轮最多四张，单张不超过 5 MiB、总计不超过 12 MiB；原始文件/Base64 不写入 Inteliscope 服务、日志、数据库或 sessionStorage。图片输入复用原版 Gateway 已有的 `chat.send.attachments`，只要求功能开关和当前模型声明 `image` 能力。历史和输出不信任任何内容块 URL：页面只读取 `messageId + partIndex`，仅当 Gateway 声明 `chat.media.ticket` 且返回 allowlisted 路径时，才获得 5 分钟、单图绑定的 Gateway 路径与票据，刷新/重连后重新申请；缺少该 RPC 时继续支持文本和图片输入，但不显示 Gateway 输出/历史图片。Handoff 升级 V7，只记录 `imageCount`，并明确图片/OCR 为不可信用户内容。
- 云端边界：浏览器 WebSocket 与媒体可统一为同一 Gateway Origin；Inteliscope 仅配置 WSS 地址和精确 HTTPS 媒体 Origin。Gateway 负责验证 `operator.read`、会话/消息归属、图片类型和允许媒体目录，再代理媒体；对象存储和长期凭据不暴露给浏览器。多副本必须共享历史/媒体索引、持久化媒体和带 `kid` 的票据签名密钥，轮换期同时接受当前及上一把密钥至少一个票据 TTL。CSP 与 `gateway.controlUi.allowedOrigins` 都只接受精确 Origin，禁止通配符。
- 原因：既有 Gateway 的媒体 URL 可能要求浏览器转发长期设备凭据，不能作为跨 Origin Inteliscope 页面图片地址；直接渲染模型返回外链又会造成跟踪、路径和内容类型绕过。把一次性授权收回 Gateway，并让前端只处理内存中规范化输入和短期 ticket，才能同时保持本机、云端和旧 Gateway 的兼容边界。

- 当前状态：已实现；不新增数据库迁移，不自动启动付费 Canary 或切换主备池。
- 决策内容：Web 新增来源以 `x_profile`、`instagram_profile`、`youtube_channel` 三个平台 setup alias 对齐 RSS、GitHub、Reddit 等普通来源；底层继续保存 `apify_social` 或 `rss`。普通 source-types 只返回业务字段与 `ready|temporarily_unavailable` 状态，不返回 Actor、Route、Build、`profile_id` 或 Key；订阅页移除 source-capabilities、support check、Actor Route 和来源级 Apify Key。X/Instagram 的 Route 与内部 binding 由服务端按平台解析，公开 config 只含 target、数量和分析模式；平台暂不可用时允许既有来源只改元数据，禁止创建、换目标或切换 enabled。YouTube 永远先使用公开 Atom Feed，Actor 仅为后端回退。
- X 恢复边界：`upgrade_legacy` 免费检查直接核对 active Primary、Backup 1、Backup 2，保留三者跨 Run 已通过的安全 Revision，并把有效候选检查上限从普通默认 12 扩为 30；公开可运行、精确成功 Build、受控输入、可验证 Dataset Schema、真实 Manifest 路径、`$0.02` Route 上限、三 Actor 唯一、至少两个发布者与内容 Canary 等底线不变。只有这三个当前 Actor 全部安全才可生成 3/3 计划，任一失败即保留兼容池并停止，不展示或自动使用替补。legacy 验证固定 300 秒与 `$0.02`，可信空结果只允许样本 1→3；样本 3、超时、合同、价格、Schema、输入或 Manifest 失败都不能靠提价、延时、样本 5 或换 Actor 绕过。
- 审批与兼容：旧 `apify_social` 请求与既有来源继续兼容但不出现在 Web 类型列表，不迁移、不改写、不停用。Route/来源付费验证必须展示逐项与总上限并单独确认；费用待结算或启动未知只 reconciliation，不重复 POST。Route 和当前 enabled 来源全部通过后仍需第二次无费用确认才原子切换 3/3，切换前旧池持续运行。
- 取代关系与原因：本决策取代 D143 中“原 Actor 不安全时为缺口选择替代项”的 legacy 行为，并针对 `upgrade_legacy` 取代 D142 的 180–900 秒、样本 5 与 `$0.10` 可调范围；D140 的旁路验证/原子 apply、D141 的 exact Build 与三 Actor/两发布者、D142 的防重复付费和 unknown-start 边界继续有效。用户创建的是平台账号而不是 Provider 路由，显示 Actor 选择会把内部实现责任错误转给使用者；X 恢复的证据又表明主要短缺来自召回，而不是安全阈值，因此只扩大当前三者的免费检查范围可以提升召回，同时避免降低合同或费用底线。

### D148 ActorOps 采用显式单路兼容、新鲜度水位与专用校验面

- 决策日期：2026-08-12
- 当前状态：已实现并完成定向验证；自动校验与付费 Actor 仍须用户显式授权。
- 决策内容：严格标准继续作为推荐方案，但不再永久阻断平台功能。严格 Discovery shortfall 后，Owner/Admin 可查看具体放宽项、保留底线和费用上限，显式选择一个公开可运行、受控输入且不超过 `$0.02` 的兼容候选；缺少 Store Schema、Tagged Build 或预先 Manifest 可由一次真实非空 Canary 生成观察型合同，能取得实际 Build 就固定，否则每次以完整 publication fence 跟随当前 Build。付费试跑和 1/3 最终生效仍分别确认，确认前旧池与来源不变。
- 新鲜度与切换：Actor 结果在日期过滤和内容合同之后，按来源水位分为 `advanced/no_advance/stale_regression`；旧内容不再增加成功计数，倒退立即软切备。同一 Candidate 连续三次 `no_advance` 后，下一次自然 schedule 暂时改用另一条健康线路，而不在当前成功任务追加付费 POST；备用推进水位后成为来源活动 Candidate，原线路六小时后可由自然任务重证新鲜。Owner/Admin 可为单个来源设置软首选 Actor，失败、旧数据或暂停仍自动回退，连续两次新鲜度通过才恢复。Route 可在独占 validation Key 上按默认 24 小时、6–168 小时或关闭的站立授权串行比较主备；三路多数、两路连续差异和单路不可交叉验证使用不同结论，任务不自动重试 Actor POST。
- 诊断与记忆：Actor/Build/Schema/价格/策略/阶段的确定性失败形成持久指纹；同指纹跳过重复 AI、input validation 和付费计划，管理员只有一次不删除历史的重试机会，证据指纹改变后自然重新评估。ActorOps 增加 Owner/Admin 数据库时间线，安全汇总发现、验证、费用、切备、新鲜度、Key 和人工动作，并镜像结构化 operation 日志；Token、真实目标、输入、正文、远端 Run/Dataset 和原始错误永不返回，日志 sink 失败不回滚业务。YouTube 仍以 Atom Feed 为主，fallback 一路即可运行，不再自动追逐第三槽。
- 迁移与取代关系：`apify_actor_resilience_v21` 使用 global schema 23，精确依赖 schema 22；离线迁移要求停 API/Worker、跨 heartbeat 安全窗、无非终态 ActorOps Job、`0600` backup、marker/table shape、integrity 和 foreign keys。既有 Route 保持 standard，不自动指定 validation Key、不启用定时校验、不自动开启兼容模式。D148 在功能明确被三 Actor/两发布者、Store Schema/Tagged Build/预先 Manifest 门槛阻断时取代 D147 的“所有底线不可放宽”和“当前三者任一失败就停止”，也取代 D103/D109/D110 中“至少两路才能运行”的限制；D140 的旧池不中断与原子切换、D142 的费用/unknown-start/防原样重付、D147 的普通来源隐藏实现字段和 YouTube Atom 优先边界继续有效。
- 原因：现实 Actor Store 并不能稳定提供三路满足完整元数据合同的候选，而严格校验本身不能替代可用功能；同时仅看 HTTP/非空响应会把持续返回旧帖的 Actor 误判为成功。把“可放宽的预先证明”与“绝不放宽的真实内容、价格、输入和人工费用边界”分开，再用来源水位、独占校验 Key、可调频率、失败记忆和统一时间线约束长期运行，能让 X 先恢复并保持可诊断、可切备和可升级。
