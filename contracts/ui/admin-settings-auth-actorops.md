## 7. Administration and authentication pages

- Subscriptions and assistant connections use the shared `admin` PageFrame within the navigation shell. `/subscriptions` exposes the same on-demand Agent rail/Drawer as Feed so run records can be added without route navigation; other administration routes do not mount it. `/settings/*` is the explicit exception: it replaces the Feed navigation shell with a dedicated Settings Workspace, so opening settings cannot mutate or visually reuse the Feed sidebar state. Its content uses the `settings` PageFrame; `/agents` and the remaining administration routes keep one route title in the Shell `PageHeader`. `/agents` has two explicit regions: “Inteliscope 数据连接” for MCP URL/delegation scope/token lifecycle, and “OpenClaw 对话连接” for Gateway URL/browser pairing/reconnect/forget-device. The peer read and subscription-management OpenClaw configuration cards use the same title/action, explanation, and code-block rows; long configuration tokens soft-wrap at any character and only vertical overflow is scrollable. In the one-time-token dialog of the connection-creation flow, the token and both setup commands use compact, right-aligned icon-only copy actions with Chinese accessible names and Tooltips; the token stays on one line and truncates its displayed tail while copying the full value, so it never causes horizontal dialog overflow. The local shell command creates `~/.openclaw/.env`, replaces only `INTELISCOPE_MCP_TOKEN`, preserves the file's other lines, and applies `0700`/`0600` permissions when the user pastes it into their local terminal; the browser never executes the local command itself. MCP token and Gateway token are never named or presented as interchangeable credentials.
- The assistant-connection page exposes `read`, `subscriptions_write`, and Owner/Admin-only `system_settings_write` as explicit, mutually exclusive choices. Creation always opens on read; unavailable choices are hidden or disabled with server-flag copy. Existing cards and one-time configurations derive from persisted access; lifecycle, focus return and destructive-action rules remain unchanged.
- Read configurations contain the 13 safe read, guidance, discovery, and diagnostic tools; subscription management adds four tools for 17 total; system management instead adds three typed setting tools for 16 total. The three peer configuration cards wrap long commands without horizontal overflow. The UI states that both write modes exclude secrets and do not grant one another's permission; server authorization remains authoritative.
- A newly issued credential retains its selected access only inside the non-dismissible one-time-token dialog. Escape and backdrop press do not close it; explicit confirmation clears the token and transient credential state from React memory.
- `/settings/notifications` exposes notifications to every signed-in account. Its first surface is the unified “通知服务” table: every service row represents exactly one Email、Webhook or Telegram destination and shows name、channel、safe configured/available/test/generation state and current business reference count. Owner/Admin create and maintain new workspace shared services; member/viewer are read-only here. Existing private v16 targets keep their original scope and owner, remain visible and selectable only to that owner, and may be paused or archived but are not offered as a new-service scope. Destination and optional signing inputs exist only in create/edit, clear synchronously at submit and never return through a query, cache, DOM node, Toast or error. Webhook service create/edit keeps the seven Provider options and Provider-specific validation.
- “个人新内容通知” contains only its master switch and an ordered multi-select of available workspace services plus the current user’s still-valid historical private targets. It never renders destination, credential or test actions and allows several services of the same channel. Apify and other system-alert settings follow the same selection-only interaction but list shared services exclusively. A paused or unavailable service remains visible with its safe reason, cannot be newly selected, and can still be removed from an existing selection. Saving a business selection cannot rename, pause, reconfigure, retest or archive a service.
- Owner/Admin 的原生 `/settings/fetching` 以 `RSSHub 服务`、`获取窗口` 和 `阅读主题库` 三个 SettingsSection 呈现既有配置；Member/Viewer 直接访问时先回到 Overview，且不请求 config 或 ActorOps 数据。RSSHub 卡固定为“服务身份与状态 → Base URL 配置 → 边界说明”三层：状态只显示 `已配置`、`未配置` 或 `环境托管` 的 StatusIndicator，固定运行密钥使用带 Key 图标的明确 secondary 操作而不占用 `SettingsItem.trailing`。专用 Modal 只接受一次 password 值，成功后清空、关闭、回焦并刷新状态；SecretStore 托管值可经独立 danger 确认移除，明确说明受访问码保护的来源会抓取失败而 Base URL/订阅不会删除。环境托管值不可在页面删除或覆盖，只说明需先由运维移除。真实值永不出现在 query、DOM、Toast、错误或响应。Base URL 仍必填、credential-free、可含安全反向代理 path prefix，640 px 起同保存按钮同行，窄屏自然单列，低频说明使用默认折叠且仍挂载的 SettingsDisclosure。
- 获取窗口仍使用既有 `set_settings_bundle` filtering payload，提供“日常抓取窗口（小时）”、Feed 活跃范围、RSS 首次抓取窗口的 7 天/30 天和历史预览条数。三个获取分区均可独立保存；多个脏分区经一次原子 bundle 保存，保存期间的新编辑不得由旧响应清除。主题库继续清理前导 `#`、空值和大小写重复项，新增、删除、撤销和保存均在本页完成。只有 filtering 保存才失效 Feed、History、Search 和 Source Health。
- A notification service has one primary configuration action: `保存并测试`. The create/update request first persists a safe draft, then the service-level test sends exactly one synthetic message for the persisted current generations; acknowledged success atomically records the Transport/service test and enables the service, while failure retains the disabled write-only-safe draft for correction or retry. Tests do not fetch, create Feed/job/outbox records or move business/service/subscription watermarks. Webhook distinguishes `provider_accepted` from `http_accepted`; every channel renders `unknown` as “请勿重复发送、先确认接收端” and never falls through to generic retry copy. Success and failure both refetch service state. Legacy target, Transport and business-level test APIs remain compatibility paths and are absent from the new UI.
- There is no separate “发送基础服务” UI group. The first Telegram service form includes the workspace Bot Token, service name and Chat ID; later Telegram services reuse the configured Bot Token unless an Owner/Admin explicitly replaces it. The first Email service form includes one of QQ、网易、Gmail、Resend or Amazon SES, its server-derived transport fields and the recipient; later Email services reuse the configured workspace sender credentials unless they are explicitly replaced. Webhook configures Provider、URL and optional signing directly. Member/viewer never receive Transport account, token or credential metadata beyond safe configured/ready/generation state, and no editable API host, proxy, parse mode, topic/thread or Telegram method is rendered.
- Replacing workspace Email or Telegram credentials advances that Transport generation, pauses the affected channel and invalidates pending deliveries. A successful service-level test restores the Transport and the tested service; other destinations whose own generation and successful test remain valid become available again without backfilling events from the paused interval. A service paused without a configuration change retains its current-generation test and can be enabled again without sending another test; enabling advances its activation watermark. Credential、Bot Token、destination and signing inputs are password-style/write-only where appropriate, clear synchronously at submit and are never refilled from a response, query cache, error, Toast or DOM. Pausing or archiving one service leaves other services usable and clearly states that paused content is neither queued nor backfilled.
- Notification services use a semantic five-column table on desktop (服务、渠道、状态、使用情况、操作). At widths below 640 px it remains a table but collapses to 服务、状态、操作: channel、scope、generation and usage move into the service cell, and neither the page nor table introduces horizontal scroll. “新增通知服务” and “编辑” use the same compact Modal pattern; per-row test, enable/pause, edit and archive actions are in an accessible More menu, while archive opens an explicit confirmation Modal that restores focus to its trigger. Pending create/save-and-test/archive/toggle actions cannot be replayed. Axe checks cover visible labels, field descriptions, focus return and disabled/read-only states for shared services and historical private targets.
- The native `/settings/secrets` form renders client validation and server failures inside its Modal and also sends a transient failure Toast. A failed create retains name, kind, provider, and environment-variable name while immediately clearing only the real Key value; success clears the whole draft and refreshes metadata. Conflict, unsupported provider, invalid environment-variable name, empty or unsafe value, and network failures use actionable Chinese copy.
- The Settings Workspace has a 260 px desktop sidebar and a separately scrolling content column capped by the `settings` PageFrame at 920 px. The sidebar starts with `返回应用`, then renders `概览`, `工作区 / 来源、获取与主题、已忽略内容`, `智能 / AI`, `通信 / 通知`, `系统 / 外观、系统参数`, and Owner/Admin-only `开发者 / 密钥、ActorOps、存储与归档`; system parameters are also Owner/Admin-only. It intentionally has no settings search. Return-state, mobile Drawer, route-title and theme behavior remain unchanged.
- Settings adopts the HeroUI Default reference only as a visual direction: solid neutral page, surface and inset layers; thin borders; moderate radii; compact controls; and the shared graphite-purple primary action. It does not use glass, backdrop blur, ambient glows or a HeroUI Pro dependency. `SettingsGroup` and `SettingsCard` expose `surface|inset`; `SettingsItem` exposes `comfortable|compact`; `SettingsDisclosure` keeps its draft-mounted content behind an accessible focusable header; and `StatusBadge` uses the same semantic border, icon gap and contrast at every page.
- Native routes additionally include Owner/Admin-only `/settings/system`. It lists all 21 typed allowlist settings grouped by capacity, jobs, retention, storage and acquisition; each row shows canonical key, environment alias, effective/source/default or override state, range, risk and effect timing. Integer and boolean drafts may be batched; reset means deleting only the DB override. Preview displays every before/after/reset, warning, expiry and exact confirmation phrase in a Modal; apply stays disabled until the phrase matches, then refreshes generation. Conflict or expiry retains a safe error and requires refresh/re-preview. Member/Viewer redirect before querying. Other native Settings routes and shared primitive boundaries remain unchanged.
- There is no Legacy Settings surface. `/settings#settings-about` redirects to Overview; old Notifications, AI, ignored, fetching, secrets, ActorOps and storage hashes redirect to their native routes only when role-authorized; unknown or role-inaccessible hashes return to Overview. `/settings/legacy` and `/settings/legacy#settings-storage` are compatibility redirects to `/settings/storage` for Owner/Admin and Overview for other roles. `/subscriptions` is the Sources bridge.
- Owner/Admin 在“助手与 AI”内先选择工作区 AI Key 与模型；Provider 仅作为所选 Key 的分类展示，不能独立编辑。两个 Key 字段使用可按名称和 Provider 搜索的紧凑 Autocomplete，选中值突出 Key 名称，Provider、连接地址类型和设置状态只作次级元数据；不再另设 Provider 框或重复连接说明。切换到不同 Provider 的 Key 时模型填入该 Provider 默认值，同 Provider 切换保留模型。独立“信息流触底文案”表单列出所有已保存 AI Key，Key 直接决定 Provider/连接地址，场景另存生成模型；首次打开旧配置时预选工作区当前 Key/模型，保存后两者不再互相跟随。启用生成时 Key 和模型必填，工作区 AI 开关不会影响已保存的显式触底绑定。表单还提供默认关闭的开关、`1/7/30` 天周期、克制/温和/轻幽默预设、最多 500 字的风格补充和每场景 `3..30` 条。文案状态使用带常驻刷新操作的单条 `SettingsDisclosure`：默认收起，摘要只显示状态、最近生成和下次更新；点击整条后同时显示空列表、首次触底和多次触底的完整文案。展开区保留稳定序号并使用一个有界纵向滚动区域，文案不截断且页面本身不被最多 90 条文案无限撑高。立即刷新只标记后台待处理，pending/refreshing 时不可重入，不将模型请求伪装成同步成功；状态读取失败只影响该区域，内置文案仍可供阅读页使用。
- Owner/Admin see native `/settings/storage` with independent 存储概览、安全治理 and 冷归档批次 sections after migration readiness. It shows stable online/cold counts and bounded database/media/archive sizes without paths or content, then offers only preview-first standard cleanup and 90-day cold archive. Archive rows use the shared compact table and More menu; restore or delete first opens a confirmation Modal and still creates only the existing preview. A preview names candidate counts, permanent stable-content deletions as zero, expiry and recheck behavior; zero-candidate cleanup/archive cannot be applied. The final owner action is danger-styled and remains disabled until the exact server-provided phrase is typed. Every pending action is non-reentrant, failures retain the preview/data, success refreshes storage, Feed, History and Search, and no control exposes SQL, raw paths or online VACUUM.
- Configured Apify Keys render as separate HeroUI `Card` listitems, each composed of `Card.Header` (identity, top-right membership status and eligible safe-drain action), `Card.Content` (one unboxed row of remaining/used/reset quota metrics and direct exception feedback), and `Card.Footer` (check time plus consistently ordered move/rotate/delete controls). `ready` renders as compact `Ready`; the pool header does not repeat the current Key. The provider is implicit in the Apify pool, and an environment-variable name appears only when it differs from the Key name. There is no `详情` disclosure: check time, block/error feedback and lifecycle actions are directly available without repeating empty work, quota cycle or visible lock copy. At 390 px the footer wraps naturally while the three metrics stay equal-width; the page itself never widens. AI Keys use the existing compact row and never query quota.
- The Apify pool shows one sticky `主用` row followed by ordered `备用` rows plus explicit `排空中/额度耗尽/无效` feedback. Each row automatically reads its safe quota projection once and caches it under a user-and-secret-scoped Query key for five minutes; the normal summary shows included-credit remaining, current-cycle usage and reset date, while a hard-limit warning appears only when it is the stricter constraint. Manual refresh bypasses freshness. During refresh or retry the existing quota remains visible, the row action is busy and non-reentrant, and its refresh icon spins unless Reduced Motion is active; the accessible busy label remains explicit either way. AI rows state `暂不支持查询` and never call the quota API. A failed row stays usable and never hides or fails either table.
- Apify standby order uses focusable up/down icon buttons with row-specific accessible names and a complete-order optimistic update. Active, draining, unresolved, or run-owning members cannot be moved, rotated, or deleted. `安全排空` is the only path that can release a busy Key; while the pool reports `draining`, its Query refetches every two seconds and all conflicting actions stay disabled. Generation conflict refreshes the canonical order before retry.
- `HORIZON_APIFY_KEY_POOL_ENABLED=false` keeps the pool visibly in compatibility mode: operators may pre-arrange idle standby order, automatic failover and drain actions remain inactive, and legacy safe rotate/delete behavior stays available. When enabled, every newly created Apify Key appears at the end of the standby queue.
- The Apify source editor never renders a Key selector in pool mode and instead shows `由工作区 Apify Key 池自动管理`; disabled rollout retains the existing source-level credential editor. The browser never receives or renders Token values, Apify account data, remote run IDs, dataset IDs, or raw upstream errors.
- Owner/Admin 的原生 `/settings/actorops` 只显示 schema-2 v2 Route。`?tab=routes|logs` 是可分享的同页双 Tab，缺失或无效参数回到 `routes`，旧 `pool|sources` 映射为 `routes`、`operations` 映射为 `logs`。Route Tab 只读取路线；日志 Tab 才读取告警、Incident 与脱敏 operation/execution events。每条路线默认展示主用/备用、LKG、Binding 就绪计数、单次费用上限和健康状态；展开后才读取脱敏的 Candidate、Store metadata、Attempt/费用、Discovery、Maintenance 与 Replacement。页面绝不读取或呈现 v1 Pool、Stage、Canary、Freshness、diagnostic event、目标、Manifest、密钥或远端 Run/Dataset。
- Route 状态在浏览器中只显示 `active` 或 `disabled`；任何遗留 `shadow` 传输值按 disabled 与 migration-required 安全呈现，不会进入旧路径。主用切换、Binding verify、费用上限、免费 metadata/Discovery 与 Replacement 仍由 Owner/Admin 的 CAS、固定确认词和服务器费用门约束；页面浏览与免费操作不启动 Actor。
- 运行日志 Tab 的顺序固定为工作区告警摘要、待处理事件、操作与执行记录。待处理事件必须同时呈现“原因 / 影响 / 下一步”和安全入口；unknown-start 只提供固定 Apify 运行记录与刷新安全日志，不提供重试或人工关闭。操作记录默认展示动作、作用范围、结果和时间，展开后只显示安全阶段、变更字段、数量、最终费用、错误码与请求结果；未识别历史动作标为“未识别管理操作”并显示经过校验的 action code。任一告警目标失败不得阻断来源抓取，页面不展示 Token、目的地、签名、目标账号、远端 Run/Dataset 或原始响应。

Their failures remain inside the corresponding Modal, submitted secret values are cleared, pending actions cannot be replayed, and dismiss/cancel restores focus to the triggering control. Successful rotation invalidates both Key metadata and that user's quota cache for the rotated secret.
